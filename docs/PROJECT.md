# Compass — Project Brief

> Compass is an AI Engineering Manager that maintains a stateful knowledge model of an engineering org and delivers one prose daily report — Yesterday, Progress, Blockers, Risks, Recommendations, Wins — that tells a manager of one to three teams what happened, what matters, what to do next, and which work does not serve the current objective.

## Problem

Engineering managers running one to three teams spend their morning reconstructing reality by hand: scanning the Jira board, chasing stale PRs, guessing whether the sprint will land, and noticing too late that a developer spent three days on work nobody asked for. The existing category (LinearB, Swarmia, Jellyfish, Pluralsight Flow) answers this with dashboards — cycle time is 2.1 days, here is your DORA panel — leaving the manager to do the reasoning, which is why the standard outcome is dashboard fatigue: opened during the trial, never again. Standup bots (Geekbot) only echo what humans typed, with no ground truth from Git or Jira. Meanwhile every product in the category is pull-only and read-only: the manager cannot tell it that Priya is interviewing all week or that the PM descoped an epic on Friday, so it confidently asserts things the manager knows are false and there is no way to correct it once and have it stick. And none of them audit whether the team's own tracker data can support the forecasts being drawn from it, so a velocity projection built on four sprints of meaningless story points is presented with the same authority as a good one. Compass replaces measurement with decisions: a deterministic analysis core computes everything arguable, a stateful org memory lets it say 'still blocked on the same dependency, day 6', a goal chain flags off-objective work with evidence, and the manager can correct it in one click or one sentence.

## Target users

Primary: an engineering manager who owns one to three delivery teams (5–8 engineers each, mixed Scrum and Kanban cadences), reads the report on a phone before standup, and is accountable for a release date upward. Secondary MVP readers: (a) a first-time evaluating reviewer with no account, no credentials and no data, who opens the app cold and must see a real generated report within 30 seconds; (b) a skip-level or director who opens a shared read-only permalink and will never create an account; (c) engineers named in report objects, who may see the team-shared report. Explicitly not the target: VP/CTO of a 100+ engineer org buying capitalization and portfolio investment reporting.

## Core features (MVP)

- Connector interface (time-windowed query port) with a seeded provider implementing it fully; the pipeline cannot detect whether data came from a seed or a live API, so real GitHub/Jira/Slack connectors drop in as a configuration change with zero changes to the knowledge model, analysis or report generation.
- Checked-in, declarative, human-readable seed dataset with a documented manifest: 3+ projects, 12 developers each holding multiple git emails plus a Jira accountId plus a Slack userId, 4 completed sprints plus 1 in-flight sprint, and planted pathologies named by ID in the manifest — one off-goal work stream, one review bottleneck on a single named reviewer, one release slipping across a multi-day window, one ticket reported blocked that was actually merged, and deliberately messy traceability (clean structural chains, branch-name-only hints, semantic-only matches, and commits with nothing at all).
- Stateful, versioned knowledge model as first-class persisted rows — Company, Objective, Project, Team, Developer, IdentityLink, Feature, Ticket, Sprint, Blocker, Risk, Recommendation — each with first_seen_at, last_seen_at and append-only status-transition history, so the report can state elapsed facts directly ('still blocked on the same dependency, day 6', 'this ticket has been resequenced twice').
- Incremental, idempotent ingest with reconciliation: re-ingesting the same window changes nothing, and when new data contradicts a stored belief a non-destructive Correction record is written and surfaced ('reported blocked yesterday; actually merged at 18:40 — correction recorded'). History is never silently rewritten.
- Injected clock: 'now' is a Clock port parameter threaded through ingest, knowledge model, sprint math and report scoping. A lint rule or test fails the build if new Date()/Date.now()/datetime.now() appears anywhere in those packages.
- Pure, unit-tested deterministic analysis layer with no HTTP, database, filesystem, clock or randomness: it takes a materialized snapshot plus an instant and returns a structured report object. An architecture test fails the build if an analysis module imports an I/O or time module.
- Deterministic analysis content: sprint completion math reconcilable line-by-line against the Jira board (committed scope, completed vs remaining, mid-sprint scope added, completion %), velocity over trailing sprints, blocker detection wired to concrete signals (Jira blocked status/flag, status dwell past threshold, PR with no reviewer, changes-requested with no follow-up), review-queue aggregation with named PRs/reviewers/ages, workload distribution, risk detection with severity and trend, wins detection with documented selection criteria, Kanban/no-sprint progress semantics, and a confidence-qualified projected completion date with its reasoning stated.
- Determinism gate: generating a report twice for the same (org, team, instant) produces byte-identical structured JSON excluding a documented allowlist of non-semantic fields (generation timestamp, run id). Same blockers, same alignment verdicts, same projected date, same confidence band — always.
- Goal hierarchy store and CRUD with effective dating: company objective → quarter → sprint goal → epic → ticket, plus ObjectiveLink records carrying source (configured | inferred | semantic).
- Three-tier alignment resolution — structural links first, then inferred links from branch names and commit messages, then semantic text matching with a confidence score — with an explicit confidence threshold, an 'unattributed' bucket rendered as a question ('3 commits could not be tied to a sprint objective') never an accusation, an OFF-GOAL verdict only at high confidence and confident attribution outside current objectives, and one-click evidence showing exactly which link or which text matched.
- LLM narration of the six fixed sections that renders the structured report and nothing else: it may choose emphasis, intra-section ordering and wording, and may not invent a blocker, risk, number, date, name or recommendation. It receives only the structured section payload, never raw events.
- Prose grounding validator: an automated extractor pulls every number, percentage, date, PR number, commit SHA, Jira key and person name from generated prose and asserts each exists in that section's structured payload; the build fails on any untraceable token. Narration fails closed — after bounded retries the report renders through a deterministic template renderer and the fallback is recorded on the report row.
- Recommendation engine producing actor + object + one-step actions ('assign Priya as second reviewer on PR #883 — open 4 days, Marcus is sole reviewer with 6 open reviews'; 'split DEV-501, 13 points, 9 days in progress').
- Per-team daily reports as the unit of record (scoped to that team's board and cadence) plus a genuine merged manager-level cross-team report that ranks what changes the manager's actions today, obeys a hard prose budget, and links down into per-team detail.
- Weekly digest: velocity trends, workload distribution, review bottlenecks, technical debt growth, upcoming risks, suggested priorities.
- Change-awareness: nothing is repeated unchanged day over day; recurring items are reported as the same item with its history and what changed.
- DIFFERENTIATOR — Manager Memos (write access to the org model): one-line prose in via email reply-to address, Slack DM/thread reply, or web form; an extraction pass converts it to a typed assertion with a closed five-kind schema {unavailable | descoped | reprioritized | external_blocker | context_note} carrying subject entity id, effective_from, effective_until|open_ended, source, raw_text; anything outside those kinds is refused with a plain 'I can't represent that yet' rather than silently swallowed; subject resolution runs against the identity/entity store and below threshold the bot replies with 2–3 candidates; the next and subsequent reports reflect the memo, cite it with a link, and stop reflecting it when it expires.
- DIFFERENTIATOR — Process Calibration Audit: the pure layer computes a fixed statistic set over trailing sprints (point-to-elapsed-working-days correlation per ticket reported with n and spread and never as a bare r, estimate coverage %, carryover rate, status-dwell consistency, scope-churn rate, sub-task double-count risk, stale-status incidence), each mapping to a named verdict against a documented threshold (points_uninformative, estimates_sparse, scope_is_fiction, workflow_inconsistent, statuses_stale, insufficient_history); verdicts are inputs to the projection method and confidence, and the report states plainly when its own numbers cannot support the claim ('your points haven't tracked elapsed days for four sprints, so this date is a cycle-time guess').
- DIFFERENTIATOR — Completion Ladder: every Yesterday item is suffixed with the furthest threshold it actually crossed, via deterministic detectors — R1 ticket in a done-category status, R2 PR merged, R3 merge commit reachable from default/release branch by branch topology, R4 a git tag or GitHub release contains the merge commit, R5 deploy-confirmed which is explicitly not inferable and renders as 'no deploy signal available'; ladder mismatches (Done with no PR, merged-not-released ahead of a release) become hygiene findings and risks naming the oldest item.
- Full feedback loop with stable item IDs derived from the underlying entity, not the report: dismiss a risk with optional reason, mark an off-goal flag wrong, accept or reject a recommendation, mark a blocker already resolved, snooze N days. Feedback is stored against the entity and changes future reports — a dismissed risk stays dismissed unless its evidence materially worsens and says why it returned; a rejected recommendation is not re-suggested; a corrected alignment flag suppresses the flag and is recorded as a correction signal against objective matching. Feedback is one click from the report in the web view, from email via signed single-purpose links, and from Slack via Block Kit actions.
- Manager-facing web view: current report, permalinked archive of every past report, per-claim source links to commit SHA / PR number / Jira key, evidence panel for alignment verdicts, and a data-freshness/coverage indicator that states what was ingested and when and degrades honestly when a source is disconnected or rate-limited.
- Simulated-clock time-travel control on the report view: step 'now' day by day or jump to any date in the seeded history, regenerating through the real pipeline for that instant, so a reviewer watches the Release 2 slip develop as the same stable item ID appears first as a risk, then as a projected slip, then as a recommendation.
- Scheduled delivery to email and Slack (DM or channel) with the full report inline and no click-to-view stub, on a per-user schedule and timezone, with per-channel subscription choice of per-team, merged, or both — defaulting a single-team manager to the team report and a multi-team manager to the merged report.
- Configuration: team membership, tracked repos and projects, goal hierarchy CRUD, and an identity roster that maps multiple git emails plus a Jira accountId plus a Slack userId to one person, with an unmatched-identity queue supporting merge and un-merge, and marking people out/inactive so they don't read as stalled.
- Auth and tenancy: email+password with Argon2id and email magic link, password reset, sessions as httpOnly+Secure+SameSite=Lax cookies with rotation on privilege change, an organization_id on every row enforced through a single scoped-query layer, and a four-role matrix (owner, manager, member, viewer) expressed as one table in code and checked server-side on every route.
- Shared report permalinks with unguessable 128-bit tokens, revocable from the report page, expiry options (7/30/90 days/never), access logging, and org-members-only by default.
- No-individual-ranking stance enforced in code: no per-developer leaderboard, no commit-count or LOC comparison across people, no top/bottom performer surface anywhere; names appear only attached to a specific, actionable, verifiable object.
- Prompt-injection containment and output sanitization: ingested text is passed as clearly delimited untrusted data to a narration model with no tool access, and rendered prose is emitted as text/markdown-with-allowlist — never raw HTML — in web, email and Slack.
- Zero-configuration cold start: a clean checkout, docker compose up (or npm run seed && npm run dev), then opening / renders a fully generated daily report for the seeded org in under 60 seconds with no login wall, no connector wizard and no empty state.
- Golden-fixture regression suite: fixtures/reports/<team>/<date>.json for at least 10 consecutive simulated days per team plus the merged report, with test:golden diffing live output and golden:update regenerating a reviewable diff, so any analysis change surfaces as a report diff.

## Out of scope

- Live GitHub, Jira and Slack API connectors, OAuth install flows, webhook receivers with signature verification, and token envelope encryption — the connector interface is built and the seed provider implements it, but no real integration ships in the MVP.
- GitHub Enterprise Server and Jira Data Center / on-premise support.
- Any integration beyond GitHub, Jira and Slack (CI/CD, PagerDuty, Linear, GitLab, Figma, calendars).
- Deploy-confirmed completion detection (ladder rung R5) — rendered honestly as 'no deploy signal available' rather than guessed.
- The multi-panel dashboard and any chart, graph, sparkline or gauge surface.
- CTO, CEO, QA and UI-Lead role views.
- Natural-language chat or Q&A over report history.
- Standalone release-date prediction beyond the sprint projected-completion date.
- Burnout detection, invisible-load tracking, and architecture-drift detection.
- The per-person 1:1 view and per-person weekly agenda (a named gap in the field, deliberately deferred).
- Right of Reply for engineers on off-goal verdicts — already judged and rejected.
- Invisible Load Ledger — already judged and rejected.
- Team-Readable Report as a distinct deliverable — already judged and rejected.
- External-dependency tracking across org boundaries (platform team, design, security review, vendor APIs) beyond what a Manager Memo of kind external_blocker can express.
- Billing, subscriptions, plans, seat purchase and payment processing.
- Seat invite/revoke/resend lifecycle and SAML/SCIM provisioning.
- TOTP 2FA and Google/GitHub SSO.
- Configurable per-org retention policies, purge scheduling, and hard deletion including backups.
- Self-serve account and organization deletion with grace period and export.
- Per-person erasure/anonymization and the 'what does Compass say about me' self-serve page.
- LLM data-minimization modes (redacted pseudonym mode, no-LLM mode) as an org setting.
- Published data-processing/subprocessor page, DPIA and GDPR Article 22 documentation.
- SOC 2, SBOM publication, dependency/secret/container scanning gates, and CSP/HSTS/header hardening as an audited program.
- Rate limiting, audit logging of privileged actions, and abuse controls beyond basic auth throttling.
- Delegated co-manager / interim cover report routing during leave.
- Catch-up mode for a manager returning after two to five weeks away.
- Mobile native apps (the web view is responsive and phone-readable; no app ships).
- Working-calendar and holiday configuration (absences are expressed only via Manager Memos of kind unavailable).
- Email delivery/bounce/complaint webhook handling and reputation management.

## Success criteria

- On a clean checkout, docker compose up (or npm run seed && npm run dev) followed by opening / renders a fully generated daily report for the seeded org in under 60 seconds with no login, no wizard and no empty state; a CI smoke test boots a clean container, fetches /, and asserts the six section headings and at least one named PR, one Jira key and one recommendation are present.
- Generating the report twice for the same (org, team, instant) produces byte-identical structured JSON excluding a documented allowlist (generation timestamp, run id); the test runs the pipeline twice in-process and diffs, and a second variant runs it in two separate processes.
- The rendered daily and weekly output in web, email and Slack contains exactly six sections in fixed order and no <canvas>, no chart <svg> and no chart library reference, asserted by test.
- A build-failing check confirms no new Date(), Date.now() or datetime.now() equivalent appears anywhere under the ingest, knowledge-model, analysis or report-generation packages, and that a Clock port is the only source of time.
- An architecture test fails the build if any analysis module imports an HTTP, database, filesystem, clock or randomness module; the analysis layer takes a snapshot plus an instant and returns a structured report object.
- An automated extractor pulls every number, percentage, date, PR number, commit SHA, Jira key and person name from generated prose and asserts each exists in that section's structured payload; the build fails on any untraceable token, and the suite includes adversarial cases where the narrator is tempted to embellish.
- When the grounding validator rejects narration after a bounded number of retries, the report renders through the deterministic template renderer, the fallback is recorded on the report row, and no ungrounded prose is ever delivered.
- Golden fixtures exist at fixtures/reports/<team>/<date>.json for at least 10 consecutive simulated days per team plus the merged manager report; npm run test:golden diffs live output against them and npm run golden:update regenerates with a reviewable diff.
- Seed fixtures are checked in as declarative human-readable files with a documented manifest and contain at least 3 projects, 12 developers each with multiple git emails plus a Jira accountId plus a Slack userId, and 4 completed sprints plus 1 in-flight sprint.
- The seed manifest names by ID at least: one off-goal work stream attributable to a non-current objective, one review bottleneck concentrated on one named reviewer, one release slipping across a multi-day window, and one ticket reported blocked that turns out to have been merged.
- A test asserts that a single generated report exercises all four traceability paths — clean structural chain, branch/commit-message hint, semantic-only match, and the unattributed bucket — and that unattributed items render as a question ('N commits could not be tied to a sprint objective') and never as an accusation.
- Every alignment verdict exposes its evidence — the specific link or the specific matched text — reachable in one click from the report.
- No commit is labelled OFF-GOAL unless confidence exceeds the documented threshold AND it is confidently attributable outside current objectives; a test asserts low-confidence cases never render as a verdict.
- Sprint completion math reconciles line-by-line against the seeded Jira board: committed scope, completed vs remaining points and tickets, mid-sprint scope added, and completion percentage all verifiable by hand.
- The projected completion date always carries a confidence band and a stated reason for that band (e.g. '40% of remaining points sit on one unestimated ticket').
- A Kanban seeded team produces a coherent Progress section with no-sprint semantics rather than a broken or empty completion percentage.
- Blockers are produced only from concrete signals (Jira blocked status/flag, status dwell past threshold, PR with no reviewer, changes-requested with no follow-up), each naming the artifact and its age.
- Every recommendation names an actor and an object and is actionable in one step; a test asserts no recommendation in the seeded output lacks a named person and a named artifact.
- The stateful model produces elapsed facts verbatim in the report — 'still blocked on the same dependency, day 6', 'this ticket has been resequenced twice' — and a test asserts these cannot be produced from a single day's event window.
- Re-ingesting the same time window twice leaves the knowledge model unchanged (idempotent reconciliation), asserted by test.
- When new data contradicts a stored belief, a Correction record is written non-destructively and the next report states the correction ('reported blocked yesterday; actually merged at 18:40'); the original belief remains queryable.
- The simulated-clock control steps 'now' day by day and jumps to any date in the seeded history, regenerating through the real pipeline; an end-to-end test walks the Release 2 window day by day and asserts the same stable item ID appears first as a risk, later as a projected slip, later as a recommendation.
- Manager Memos: a memo 'Marcus is out Jul 27–Aug 2' sent by Slack DM causes the next simulated day's report to drop Marcus's stalled-work finding and state the reason with a link to the memo; a descoped memo changes the sprint completion percentage and annotates the change; an out-of-schema memo receives a plain refusal; a memo whose subject resolves below threshold gets a reply offering 2–3 candidates; an expired memo stops affecting reports.
- Process Calibration Audit: the seeded slipping release yields a points_uninformative verdict whose stated n and spread match a hand-computed check, the projected completion date in that report is produced by the cycle-time method and says so in prose, and a seed-manifest variant without estimation noise clears the verdict and switches the projection method.
- Completion Ladder: Yesterday items on the seeded repos show all four detectable rungs correctly, verifiable by hand against the seeded branch topology and tags; a seeded ticket marked Done with no PR produces a hygiene flag; the pre-release seeded state produces a merged-not-released risk naming the oldest item; rung R5 renders as 'no deploy signal available'.
- Feedback loop: dismissing a risk suppresses it in subsequent reports; it resurfaces only on material worsening of its evidence and states why it returned; a rejected recommendation is never re-suggested; a corrected off-goal flag is suppressed and recorded as a correction signal against objective matching; a blocker marked resolved does not reappear; a snoozed item returns after exactly N simulated days.
- Item IDs are derived from the underlying entity and are stable across reports: an end-to-end test asserts the same risk on two consecutive simulated days is one item with a history, not two items.
- Change-awareness: a test asserts no item is delivered with identical prose and no stated change on two consecutive days.
- A manager configured with three teams receives per-team reports and a merged report; the merged report stays within its documented prose budget, is not a concatenation (a test asserts items are ranked and dropped, not stitched), and every merged item links to its per-team detail.
- Per-channel subscription works: a subscriber can select per-team, merged, or both independently for email and Slack, on their own schedule and timezone; a single-team manager defaults to the team report and a multi-team manager to the merged report.
- Email and Slack deliveries contain the full report inline with no click-to-view stub, and a test asserts the six sections are present in both channel renderings.
- Feedback is actionable in one click from the web view, from a signed single-purpose single-use email link scoped to one item and one action, and from a Slack Block Kit action; each path mutates the same entity-scoped state.
- Every past report is permalinked, archived and shareable via an unguessable 128-bit token that is revocable from the report page, defaults to org-members-only, and supports 7/30/90-day or never expiry.
- A two-org isolation test creates identical-looking data in both and asserts that no API route, report permalink, export or email link exposes one org's data to the other.
- A parametrized authorization test iterates every (role × route) pair across owner, manager, member and viewer and asserts the server-side outcome matches the single role matrix table in code.
- Every report claim links to its source artifact (commit SHA, PR number, Jira key); a test asserts no claim in the seeded output lacks a source link.
- The freshness/coverage indicator states what was ingested and when, and when a source is marked disconnected or rate-limited the report says so explicitly instead of silently reporting on partial data.
- The roster maps multiple git emails plus a Jira accountId plus a Slack userId to one person; the unmatched-identity queue supports merge and un-merge; a person marked out/inactive is never reported as stalled.
- A codebase test asserts no per-developer leaderboard, commit-count comparison, LOC comparison or top/bottom-performer surface exists in any renderer or API response.
- A ticket titled with a script tag and an email-header injection payload appears as literal text in web, email and Slack with no execution and no header injection.
- Ingested text reaching the narration model is passed as clearly delimited untrusted data, the narrator has no tool access, and an injection test asserting an embedded 'ignore previous instructions' in a commit message does not alter the report structure or content.
- A manager reading the seeded daily report can name, without opening Jira or GitHub, the sprint completion percentage, the projected date and its confidence reason, the top blocker with its age, the review bottleneck's reviewer and queue depth, at least one off-goal or unattributed item with its evidence, and one recommendation they could execute immediately.

## Constraints

- No real GitHub, Jira or Slack credentials exist at build time — the seeded provider must be the runtime substrate for the entire MVP, and every code path must be exercisable without a live API.
- Determinism is a hard requirement, not a preference: the same (org, team, instant) must yield identical blockers, alignment verdicts, projected date and confidence band on every run.
- The LLM may not originate any factual claim; every number, date, name and identifier in the prose must exist in the structured report, enforced by an automated grounding test that fails the build.
- Prose-first, no-chart discipline: no chart, sparkline, gauge or graph anywhere in daily or weekly output, asserted by a test on the rendered output.
- Exactly six sections in fixed order (Yesterday, Progress, Blockers, Risks, Recommendations, Wins) across web, email and Slack.
- The daily report must be readable in about 90 seconds on a phone; the merged multi-team report has a hard prose budget and must prioritise rather than concatenate.
- Zero-configuration first run: no login wall, no connector wizard, no empty state, report rendered in under 60 seconds on a clean checkout.
- 'now' may never be read from the system clock inside the pipeline.
- No individual ranking or per-developer productivity comparison may exist anywhere in the product, enforced in code.
- Every claim must link to its source artifact (commit SHA, PR number, Jira key); nothing unverifiable ships.
- Multi-tenant isolation by organization_id on every row through a single scoped-query layer, verified by a two-org test asserting no route, permalink, export or email link leaks across.
- Manager Memos accept only the five defined assertion kinds; out-of-schema input is refused explicitly, never silently absorbed.
- Report quality on the seeded dataset is the sole acceptance bar for the MVP; breadth of surface area is not.
- Solo/small build team, so the MVP must be deliverable without a live-integration environment, load testing infrastructure, or an enterprise compliance program.

## Assumptions

- Platform is a responsive web application, phone-readable, plus email and Slack delivery; no native mobile app.
- Live GitHub/Jira/Slack connectors, OAuth flows and webhook receivers are out of MVP scope even though the interface they will implement is built and fully exercised by the seed provider; the user stated credentials will not exist at build time and that the swap must require no pipeline changes, which the connector interface plus a conformance test satisfies without shipping the integrations.
- The MVP ships a single seeded organization; multi-tenancy is enforced structurally (organization_id everywhere, scoped-query layer, role matrix) but no org-provisioning or signup funnel is built.
- The zero-configuration first-run report is served without authentication as a public demo of the seeded org; authentication gates configuration, feedback writes and Manager Memos.
- Billing, seat lifecycle, 2FA, SSO, retention policy configuration, per-person erasure, account deletion, audit logging, rate limiting, security header hardening and compliance documentation are deferred; the user's stated judging bar is report quality on the seeded dataset, and these do not affect it.
- The narration model is Claude via the Anthropic API, with prompt/response tracing and a deterministic template renderer as the fail-closed fallback.
- Semantic alignment matching uses embedding similarity between commit/ticket text and objective descriptions, with a documented, configurable confidence threshold and checked-in fixtures so its outputs are reproducible; the semantic step is treated as a pure function of its inputs for determinism purposes.
- Determinism is defined over the structured report object only, not the LLM prose. Prose may vary run to run; the grounding test guarantees it introduces no new facts. Golden-file tests assert on structured JSON.
- 'Yesterday' means the 24-hour window ending at the injected instant, on the team's configured timezone; the merged report uses the manager's timezone.
- Sprint and objective data (sprint goals, epics, the goal hierarchy above them) come from the seeded dataset for the demo path and from configuration for a real org; company/quarter objectives are always manually configured because no source system holds them.
- 'Confidence band' for the projected completion date is a fixed ordinal set (high / medium / low) with documented threshold rules, not a numeric probability.
- Story-point estimation is assumed inconsistent in real orgs; the projection engine supports at least two methods (velocity-based and cycle-time-based) and the Process Calibration Audit verdicts select between them.
- The seeded dataset spans roughly five sprints (four completed plus one in flight, about 10 weeks) with a dozen developers across three projects, including at least one Kanban team and at least two Scrum teams on different cadences.
- The merged report's prose budget is a fixed word/character ceiling per section plus a fixed maximum item count, both documented and test-asserted; the ranking function scores items by change-since-yesterday, severity, blast radius across teams, and whether an action is available today.
- Slack ingestion in the seeded dataset represents opt-in named channels only; no DM or private-channel content exists in the seed, matching the privacy stance the product will hold with real credentials.
- Manager Memo subject resolution uses the existing identity/entity store with a documented confidence threshold; the extraction pass is the only LLM use outside narration, and its output is validated against the closed five-kind schema before persistence.
- 'Material worsening' that resurfaces a dismissed risk is defined by explicit per-risk-type rules over the risk's evidence (e.g. severity increases a level, age crosses the next threshold, blast radius grows to include the release branch), documented and unit-tested rather than left to model judgement.
- Wins selection criteria are deterministic and documented (e.g. highest completion-ladder rung reached, objective-aligned delivery, a blocker cleared, review debt reduced), capped at a fixed count per report.
- Weekly digest recipients, cadence and delivery reuse the same subscription, schedule and timezone mechanism as the daily; it is not separately configurable in the MVP.
- 'Technical debt growth' in the weekly digest is derived only from already-ingested signals (labelled debt/refactor tickets, unattributed maintenance work streams, changes-requested churn) and does not involve static analysis or code-quality scanning.
- The feedback loop, per-team plus merged reports, web view, email/Slack delivery, light configuration, and all three differentiators are treated as MVP because the user explicitly asked for the most complete and desirable product and accepted the extra build time; the MVP is therefore wider than a minimal daily-report build, and the deferrals above are what keeps it finishable.
- Data volumes are small (three teams, twelve developers, ten weeks of history), so no performance, scale, caching or background-job-scaling work is in scope beyond keeping cold-start report generation under 60 seconds.
- Report generation runs synchronously on request for the demo and simulated-clock paths, and on a scheduler for delivery; no distributed queue is required at this scale.
- The build is a greenfield repository with no existing systems to integrate, and the target reviewer evaluates it by cloning and running one command.
